# Dream-Store code audit and fixes — 22 October 2026

Baseline: `4a533c8ecd1c55b7b857067ceae0568edb5eea4d` on `main`.
Scope: V1 production source, V2 staging source, browser/API contracts, private files,
financial writes, receipt delivery, session restoration, and existing release gates.
This is a source audit and local verification report, not paid-production approval.

## Corrected defects

| Area | Finding | Correction |
| --- | --- | --- |
| Browser checkout | Keys contained colons and payment-reference text, exceeded API limits, and were incompatible with V2. | Use bounded random keys, retain the key across failed-response retries, and store only an intent hash and key in tab storage. Clear the attempt after confirmed success. |
| V1 checkout retry | A successful order followed by a lost response left the buyer receiving 409 on every retry. | Return the committed order on an identical retry. Reject a reused key with different purchase details. Return saved counters and token without creating another order. |
| V1 financial consistency | Duplicate payment references were checked in process memory. Concurrent instances could accept the same transfer. | Claim the normalized Seller/method/reference in the order transaction, including checks against legacy ledger rows. The order-created audit is committed with the financial records. |
| Order identifiers and currency | Order IDs used a small random suffix; inherited object keys could pass currency validation. | Use UUID identifiers and own-property currency checks. |
| V2 signing failures | Checkout could commit financial records before discovering that signing was unavailable. | Check signing configuration before creating any order. |
| Download retries | The UI ignored V2's replacement token. An older poll could also overwrite a newer token/count. | Store replacement tokens, keep download state monotonic while paid, and always accept an authoritative refund/rejection revocation. |
| Buyer rights | Waiving a Seller/platform commission set `commissionStatus=reversed`, which incorrectly revoked a paid Buyer's file access. | Determine delivery from payment/refund state, ownership, expiry, usage and token. Validate expiry/count/limit values strictly. |
| V1 uploads | Suspended stores, mismatched file signatures and ownership changes during upload were not consistently rejected. | Validate bytes before storage, read current store permissions, use create-only private objects, verify metadata, and recheck ownership/status transactionally before publishing the file pointer. Compensate failed writes. |
| V1 publication | Ownership or file changes between validation and saving could escape a final check; public-token originals could be published. | Commit publication transactionally against current store/product/file records. Reject public download tokens and pin the verified object generation. |
| V1 delivery | A process-local cache could serve an obsolete original after another upload. File privacy/version changes were not fully checked. | Read the current private pointer for every download, check public-token exposure and file bytes/version, then recheck the pointer while committing the usage counter. Remove the obsolete deliverable cache. |
| Email receipts | An unconfigured, rejected or failing provider was still reported as `sent`. Notification state was not persisted with the ledger. | Report skipped/failed/sent accurately, use a bounded provider timeout, omit raw provider errors, and persist receipt state in the ledger and notification record. |
| Account changes | Previous account privileges could remain visible during asynchronous verification; order JSON could finish after effect cancellation. | Clear privilege/profile state before awaiting verification, gate private listeners on the verified profile, abort old polling and recheck cancellation after JSON parsing. |

## 23 October 2026 — production follow-up

Further V1 regressions reproduced and corrected:

- Download-token issuance and final file-release transactions now share the strict
  payment/expiry/count/limit policy already used by V2. Malformed counters and an
  invalid expiry introduced during file retrieval previously passed authorization.
- Commission updates now commit the rate and an immutable audit together under
  `platform_settings/commission`. Every reader reloads that authoritative record;
  a missing document retains the 500 bps default. Invalid records fail closed and
  can be repaired through the existing verified Super Admin API. Confirm the
  intended current rate before deployment because prior process-only overrides
  cannot be recovered from Firestore.
- Checkout snapshots commission configuration within the order transaction, so a
  concurrent rate change cannot produce inconsistent calculations. Existing orders
  retain their original rate, including on idempotent retries.
- Readiness now includes commission configuration. A regression proves that an
  invalid configuration returns 503, liveness remains available, and an audited
  repair restores readiness. This is a synthetic regression, not a diagnosis of
  the live service's 503.
- Zero commission stays zero in buyer, seller and administrator calculations.
  Failed administrator saves show an error instead of claiming a local success.

Local checks passed: TypeScript, production build, 42 server/configuration tests,
4 browser-protocol tests, 110 V2 tests, 4 offline preflight tests and 51 contracts.
